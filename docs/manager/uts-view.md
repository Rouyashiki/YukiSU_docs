# UTS View

UTS View 改变进程从 UTS namespace 看到的内核身份，包括 `uname` 相关字段。它提供“视图”，不会替换正在运行的内核、修改真实 KMI，或改变内核安全补丁级别。

入口在“设置 → UTS View”。当前运行 LKM 不支持 UTS View 时，设置项会显示不支持并禁用。

## 可以改哪些字段

页面分别控制六个 UTS 字段：

- `sysname`；
- `nodename`；
- `release`；
- `version`；
- `machine`；
- `domainname`。

每项都有独立开关。被选中的值不能为空，且最多 64 个 UTF-8 字节；这里限制的是字节数，不是界面显示的字符数。

::: warning 保留原始内核身份
修改 `release` 或 `machine` 只改变 UTS 查询结果，启动属性、文件及其他内核接口仍提供各自的信息。安装器、模块或诊断脚本如果依赖修改后的值判断兼容性，就会按该值选择路径；下载 LKM 和排错时使用页面保存的原始身份。
:::

## 三个配置目标

| 目标 | 作用范围 | 生效时机 | 主要限制 |
| --- | --- | --- | --- |
| 运行时全局 | 仍共享初始 UTS namespace 的任务 | 保存后立即更新可覆盖的任务 | 已有私有 UTS namespace 保留旧身份；早启动锁定时不可修改 |
| Denylist 作用域 | 之后进入 denylist 作用域的应用进程 | 目标应用下次启动/特化 | 已运行进程不变，修改后要彻底重启目标应用 |
| 早启动全局 | 下一次启动从 LKM 早期建立的全局身份 | 重新修补、刷入正确槽位并完整重启 | 本次启动会锁定全局身份，不能再用运行时全局覆盖 |

运行时全局与 Denylist 作用域可以同时启用。页面状态会显示“全局 + Denylist 作用域”。

Denylist 作用域没有独立的包名列表。普通应用是否进入该作用域，由 [Non-root Profile 的“卸载模块”策略](/manager/app-profile/)决定；Root 应用和管理器不进入，隔离进程另行纳入。所有符合条件的新进程共用同一份 Denylist 模板；已经拥有私有 UTS namespace 的进程不会再应用这份模板。

## 状态页怎么读

### 配置来源

- **早启动：** 当前全局身份来自随 LKM 启动的早期配置；
- **运行时：** 当前配置由设备侧持久配置在 `post-fs-data` 恢复或由页面写入；
- **未配置：** 没有活动的 UTS View 模式。

### 早启动锁定

早启动全局配置在本次 boot 已经生效时，页面把全局身份标为锁定。此时运行时全局开关被禁用；要更改或关闭，必须重新修补目标启动链并重启。

Denylist 模板仍是单独的作用域，不因全局锁定而自动等同于全局模板。

### 原始身份有效

页面同时显示：

- 内核捕获的原始身份；
- 当前全局有效身份。

“原始身份有效”表示内核保存了用于诊断和 KMI 选择的原始快照。LKM 支持 UTS View、但原始 `release` 不可用时，安装页会拒绝自动 KMI 检测；从目标原厂启动镜像确定 KMI 后手动选择。

### Late capture 与 coverage gaps

- **原始身份捕获过晚：** LKM 在系统启动后才加载，原始快照来自加载时，无法追溯加载前的身份和任务；
- **存在运行时缺口：** 部分任务已经拥有私有 UTS namespace，无法接收运行时全局更新。

运行时更新无法修改已有私有 namespace。需要从启动阶段建立全局身份时，配置早启动全局模板、重新修补并完整重启。

## 早启动配置如何进入 LKM

页面中的早启动模板先保存在管理器本地，并暂存一份待修补配置。点击“重新修补”会进入只提供当前槽位/未使用槽位安装的修补流程；也可以回到普通安装页，让之后的受支持修补带上这份暂存配置。

- 传统 Ramdisk 路径把模板编码为 LKM 启动参数；
- ImgPatch 路径把模板写入 LKM 的 512 字节 ImgPatch 配置块。

离开页面时若仍有未修补的变化，会提示重新修补。暂存文件损坏或模板无效时，管理器会阻止修补；返回 UTS View 修正字段并重新保存后再试。

::: important 安装后完整重启
选择修补文件时，把输出镜像刷入目标固件对应的 `boot`/`init_boot` 和槽位。选择直接安装时，确认安装完成并完整重启。回到 UTS View，确认配置来源为“早启动”、锁定状态为“是”，再查看有效身份。
:::

## 操作步骤

### 测试应用的 Denylist 视图

1. 在超级用户页打开目标应用，保持未授予 Root，并在自定义 Non-root Profile 中开启“卸载模块”；全局 Kernel Umount 开启时，这也会改变它的模块可见性；
2. 回到 UTS View，开启 Denylist 作用域，只开启必要字段并填入值；
3. 保存后彻底结束目标应用，再重新启动；
4. 在目标进程中读取 `uname`，不要用终端应用的结果代替；
5. 同时保留原始身份和目标进程的结果，并检查其他使用同一模板的应用。

### 需要当前系统大范围立即变化

1. 先记录“原始身份有效”和当前有效身份；
2. 使用运行时全局；
3. 查看页面是否报告 coverage gaps；
4. 已有私有 namespace 的进程保留旧值；需要更新它们时，改用早启动全局模板并完整重启。

### 需要从早启动覆盖

1. 配置早启动全局模板；
2. 保留目标固件原厂镜像；
3. 从页面进入重新修补，核对槽位与修补模式；
4. 完整重启；
5. 确认来源为“早启动”、早启动锁定为“是”，并比较原始/当前身份。

关闭早启动模式同样需要重新修补和重启，仅关闭页面开关不会修改已经刷入的 LKM。

## 排障时必须同时记录

- 当前配置来源与模式；
- 早启动锁定、原始身份有效、late capture 和 coverage gaps；
- 原始与当前 `release`；
- 启动镜像实际解析出的 KMI；
- 最近一次修补的目标分区、槽位和工作模式。

同时提供原始身份和目标进程的 `uname -a`；后者显示的是该进程实际使用的 UTS 视图。

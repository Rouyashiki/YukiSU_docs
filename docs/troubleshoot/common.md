# 常见问题排查

先别把所有开关都拨一遍。YukiSU 有 LKM、管理器认证、`ksud`、普通模块、MetaModule 和 YukiZygisk 好几层；找错层，日志看得再多也只是在绕路。

## 先把问题归类

| 现象 | 最可能的层级 | 第一份证据 |
| --- | --- | --- |
| 设备刷入后无法启动 | 启动镜像、分区、槽位或 LKM | 刷写记录、原厂镜像、bootloader 状态 |
| 系统能启动，管理器显示未安装 | LKM 未加载或启动链没有生效 | 管理器首页、完整内核日志 |
| 显示已安装，但管理器无权限 | 包名/签名或 SuperKey 认证 | 认证模式、APK 来源、设备时间 |
| 修补、恢复或 OTA 后安装失败 | 输入镜像、工作模式、目标 KMI/分区/槽位 | 完整安装输出、输入来源、操作前后槽位 |
| 首页提示 `ksud` 被替换 | 设备侧守护进程与当前管理器不一致 | 内置版本、已安装侧的未知/不一致状态、告警时间 |
| 功能开关保存失败或回滚 | 内核不支持、持久化或即时应用失败 | 开关名、提示信息、前后状态 |
| Root 可用，模块脚本不运行 | `ksud`、安全模式或模块状态 | `ksud` 版本、模块状态、启动日志 |
| 脚本运行，但系统文件没出现 | MetaModule 或 mount namespace | MetaModule 状态、`metamount.sh` 日志 |
| 普通模块正常，Zygisk 模块无效 | YukiZygisk、ABI 或目标进程 | YukiZygisk 状态页与管理器 bugreport |
| 更新后才出现异常 | 版本组合或待处理状态 | 更新前后版本、第一条错误、变更清单 |

挑最像的一行往下查。名字里有 “SU”，不代表模块 WebUI 打不开也得怪内核。

## 收集最小环境信息

如果设备还能正常进入 Android，并且 ADB 已经授权，可以先用只读命令记录基本信息：

```sh
adb shell getprop ro.product.cpu.abi
adb shell uname -a
adb shell getprop ro.build.fingerprint
adb shell getprop ro.boot.slot_suffix
```

如果启用了 UTS View，普通 `uname` 可能显示的是修改后的身份。还要记录管理器 UTS View 页面中的原始内核身份，并以目标镜像实际解析出的 KMI 为安装依据。

同时从管理器首页记录：

- YukiSU / LKM 完整版本；
- 原始与当前内核版本、Hook 类型和工作模式；
- 管理器版本；
- 内置与已安装 `ksud` 版本；
- 当前认证方式；
- MetaModule、YukiZygisk、安全模式与相关 Feature 状态。

日志先找**第一条直接错误**。后面几十行红字，很多只是前面那一处失败后的连锁反应。

## 先分清工作模式

首页“工作模式”把 Hook 类型与加载方式放在一起显示。后半部分决定该去哪里找证据：

| 模式 | LKM 从哪里进入 | 排障重点 |
| --- | --- | --- |
| Ramdisk | 启动 Ramdisk 中的 YukiSU 链路 | `boot` / `init_boot`、Ramdisk payload、早期启动日志 |
| ImgPatch | LKM 直接嵌入 `boot` 内的 ARM64 内核 Image | 原始 `boot`、目标 KMI、ImgPatch 修补/恢复输出与备份 |
| Lateload | Android 启动后临时加载 | 当前会话的加载输出、SELinux 前置条件；重启后消失属于预期 |

这三种状态不能用同一套恢复思路。ImgPatch 不等于“把 `.ko` 放进 Ramdisk”，Lateload 也不等于已经持久安装。报告问题时不要只写“LKM 模式”。

## LKM 无法加载

### 现象

- 管理器显示 YukiSU 未安装；
- LKM 版本为空或无法读取；
- 刷入后系统仍能启动，但没有任何 YukiSU 内核能力；
- 内核日志出现 module、vermagic、symbol 或 relocation 相关错误。

### 排查顺序

1. **确认设备范围**：Android 12 及以上、ARM64、GKI 2.0（Linux 5.10 及以上）；
2. **确认实际启动镜像**：修补的是当前固件、当前启动路径使用的镜像；
3. **确认槽位**：A/B 设备当前启动槽位与写入槽位符合计划；
4. **确认 KMI**：LKM 与目标内核 KMI、符号版本和构建配置一致；
5. **确认内核能力**：Kprobes、Kretprobes、syscall tracepoints 可用；
6. **查看首条内核错误**：不要只截取最后一行 “failed”；
7. **回到已知良好状态**：如果无法确定输入镜像，先恢复匹配的原厂镜像重新判断。

### 不要这样做

- 不要强制加载不匹配 `.ko`；
- 不要关闭模块版本或符号检查来“试试看”；
- 不要把另一台同机型设备的 LKM 直接视为兼容；
- 不要在不清楚活动槽位时连续对两个槽位写入。

版本检查把不匹配的 `.ko` 挡在门外，其实是在帮你。强行绕过，只会把一条清楚的“拒绝加载”换成更晚、更难救的内核故障。

正式构建当前提供的 KMI 目标是 `android12-5.10`、`android13-5.10`、`android13-5.15`、`android14-5.15`、`android14-6.1`、`android15-6.6`、`android16-6.12` 与 `android17-6.18`。这张表描述预构建产物，不代表同名 KMI 下的每个厂商内核都必然能加载；vermagic、符号版本与厂商改动仍需匹配。完整边界见[兼容范围](/guide/compatibility/)。

## 镜像修补或恢复失败

先保存完整输出，再确认走的是传统 Ramdisk 路径还是 ImgPatch。当前管理器可以处理本地镜像、从 URL 提取 OTA/工厂镜像、直接安装和 OTA 后安装到非活动槽位；入口相似，目标却不一样。远程 URL 入口当前只走传统 Ramdisk 修补；ImgPatch 只出现在本地镜像、设备直装与非活动槽位的内核直嵌分支。

### 修补前

1. 输入必须属于当前设备和准确固件，远程 URL 也不例外；
2. 让管理器从目标镜像解析 KMI；只有自动判断不出来时才人工选择，并记录理由；
3. 核对选中的 `boot` / `init_boot`、当前槽位与目标槽位；
4. “安装到非活动槽位”只用于 OTA 已完成、尚未切槽重启的窗口；
5. 选择“备份为原厂镜像”时，输入必须真的是未修改原图。

### ImgPatch 特有边界

- ImgPatch 只修补 `boot` 中的内核 Image；设备直装时还会清理已知的旧 KernelSU Ramdisk payload；
- Shell Root、USB 调试和早启动 UTS 配置会写入本次使用的 LKM，修改后需要重新修补并完整重启；
- 更新已有 ImgPatch 时可以原位替换 LKM，但“更新成功”仍要以重启后的首页工作模式、版本和内核日志为准；
- 恢复流程会验证原始镜像备份。若输出提示备份带有 ImgPatch capsule、无法验证或退回手动清理，不要把它当成已经恢复原厂。

保留原始镜像、修补输出、生成文件的哈希以及实际写入记录。只有生成了输出文件，不代表目标分区已写入；只有写入成功，也不代表下一次启动已经验证。完整流程见[安装与镜像模式](/guide/install-modes/)。

## 管理器显示已安装但无法认证

首页连 LKM 版本都读不到，先查加载；能读到版本、授权页面却进不去，才重点查认证。别把这两个问题混在一起。

### 使用默认签名认证

- APK 是否来自 [YukiSU Releases](https://github.com/Rouyashiki/YukiSU/releases/latest)；
- 包名与 APK 签名是否保持官方预期；
- LKM 是否来自同一项目，而不是其他 KernelSU 分支；
- 是否曾在安装时启用“禁用 APK 签名验证”。

### 使用 SuperKey

- LKM 构建是否包含 `CONFIG_KSU_SUPERKEY=y`；
- 输入密钥是否与编译或修补时写入的一致；
- 设备日期和时间是否明显错误；
- 请求是否落在认证允许的时间窗口；
- 是否把全角字符、前后空格或不同编码误当成同一密钥。

不要公开 SuperKey、带密钥的修补参数或包含密钥的 LKM 构建日志。忘记密钥且签名认证已被禁用时，应重新修补并安装一个信任配置明确的 LKM。

## Root 请求没有弹窗或被拒绝

1. 确认管理器已经认证，而不是只安装了 APK；
2. 检查应用是否出现在超级用户列表，授权是否被明确拒绝；
3. 检查请求是否来自预期包名、UID 与进程；
4. 暂时恢复该应用的默认 App Profile，排除错误身份或 SELinux domain；
5. 检查 sulog 或相关诊断中的调用方和结果；
6. 彻底结束目标应用后重新测试新的 `su` 请求。

改完授权后要重新发起 `su`。已经拿到 Root 的进程不会看见你点了“拒绝”就自觉降权。

## `ksud` 版本不一致或被替换

管理器 APK 内置一份 `ksud`，设备的 `/data/adb/ksud` 是另一份已安装状态。常见现象包括：

- 管理器能认证，但模块操作或工具失败；
- 首页提示内置与已安装版本不同；
- 首页或系统通知提示设备侧 `ksud` 与当前管理器不一致；
- 更新管理器后，新功能显示但后端命令不认识；
- 启动日志提示 UAPI 或版本不匹配。

新版 `ksud` 会监视自身安装路径，管理器也会核对设备侧文件。告警可能是管理器更新后尚未同步，也可能是其他 Root 管理器或进程替换了它；它不是只看文件名得出的结论。

先记下内置完整版本、已安装一侧的原始显示和告警时间，再打开首页的“`ksud` 守护进程”详情。二进制不匹配时，管理器不会执行这份不受信文件来查询版本，因此已安装一侧显示“未知”属于有意的安全行为，不是缺一份必须从首页读出的版本。确认当前 APK 来源可信后，才使用页面按钮恢复内置版本；“自动更新 `ksud`”默认关闭，开启后会在应用冷启动时同步。同步完成后重新打开详情并检查启动日志。

别从别的分支抓一个也叫 `ksud` 的文件覆盖过去；文件名一样，不代表它们说同一种协议。若文件再次被替换，应先找出执行替换的管理器、脚本或模块，而不是循环覆盖。同步选项与软重启边界见[设置与维护](/manager/settings/)。

## Feature 开关失败、未生效或显示不支持

“功能控制”页面向当前运行内核查询 Feature 支持与状态。管理器的 KernelSU 分组包含上游兼容 `0–4`，以及 YukiSU 在上游预留区实现的 WebView Zygote 卸载 `5`；YukiSU 扩展为 `100–104`。状态有三层：内核当前值、`ksud` 持久化配置，以及某些功能的即时用户空间动作。

- “内核不支持”通常说明正在运行的 LKM 太旧或构建时没有相应实现，更新 APK 不会凭空增加内核能力；
- 页面提示失败或开关回滚时，保留提示与日志，不要按到 UI 看起来保持开启为止；
- SELinux Hide、WebView Zygote 卸载等会明确要求重启；
- ADB Root 切换还要重启 `adbd`，Magisk 风格 su 弹窗还要应用/撤销可见 `su` 挂载；后续动作失败时新版管理器会回滚 Feature 状态；
- YukiZygisk、早启动 UTS 与 ImgPatch 内嵌配置有启动时快照或早期生效边界，应按页面提示完整重启或重新修补。

完整重启前先保存失败状态。软重启会停止并重新启动 Android 服务、重跑模块阶段，但不会重新加载 LKM，也不会重新执行 bootloader、内核和早启动 Image 配置；验证 LKM、ImgPatch、槽位或明确标注“重启生效”的安全开关时，以完整重启为准。11 个开关的准确边界见[功能控制](/manager/feature-control/)。

## 模块脚本没有运行

依次确认：

1. 模块不是禁用或待卸载状态；若正在待更新，先完成一次正常重启并确认实际生效版本；
2. YukiSU 没有进入会禁用全部模块的安全模式；
3. 模块脚本使用 Unix 换行、正确 shebang，并且安装后权限合理；
4. `post-fs-data.sh` 没有等待尚未启动的 framework 或网络；
5. `ksud` 与 LKM UAPI 没有版本错配；
6. 启动日志中能看到对应阶段开始与模块错误。

如果某个脚本必须依赖挂载后的文件，应移动到 `post-mount` 或更晚阶段，而不是在 `post-fs-data` 中假定 MetaModule 已完成。

## 模块安装成功但文件没有挂载

### 先确认模块确实需要挂载

模块只有脚本、`system.prop` 或 `sepolicy.rule` 时，本来就可能没有系统文件挂载。检查模块是否包含 `system/` 文件树，以及是否存在 `skip_mount`。

### 再确认 MetaModule

- 只存在一个活动 MetaModule；
- 没有 `disable`、待更新或待卸载状态；
- MetaModule 遵循上游接口，且具体后端支持当前设备与普通模块需求；
- `post-fs-data.sh` 和 `metamount.sh` 没有失败；
- 普通模块安装时的 `metainstall.sh` 处理没有报错。

### 最后确认 namespace

Root shell 看得到、只有目标应用看不到，八成要查 namespace 或模块卸载策略。到处都看不到，才更像 MetaModule 根本没挂成功。

若只有 WebView 或 WebView sandbox 内看不到修改，检查“为 WebView 卸载模块”（Feature `5`）。在全局 Kernel Umount 仍启用的前提下，它会让 UID 1053 的 WebView zygote 在派生 sandbox 进程前获得干净挂载视图；关闭全局机制会让这里也无法卸载。代价是修改 WebView 资源的模块可能失效，改动后要重启再判断。

不要同时更换 MetaModule、更新普通模块和修改卸载策略；一次只改变一个变量。

## 模块导致系统异常或启动变慢

- 从最近安装或更新的模块开始禁用；
- 一次只处理一个怀疑对象；
- 检查 `post-fs-data.sh` 是否阻塞；
- 检查 `service.sh` 是否创建崩溃重启循环；
- 检查多个模块是否覆盖同一目标文件；
- 必要时进入 YukiSU 安全模式，让普通模块全部禁用。

安全模式一开就正常，模块层嫌疑最大；安全模式也救不了，再看 LKM、启动镜像或系统本身。

## YukiZygisk 已启用但模块无效

“开关打开”“发现模块”“已经注入”“模块真有用”是四步，别看到第二步就宣布兼容成功。

1. 确认普通 Root 稳定；只有待测模块依赖 `system/` 等文件挂载时，才把 MetaModule 作为前置层核对；
2. 确认 YukiZygisk Feature 已启用，且没有进入安全模式；
3. 确认模块类型是普通 Zygisk 模块还是 Native ZN 模块，并核对 64/32 位 ABI；
4. 对 Native ZN 模块确认使用受支持的 Zygisk Next Native API 3/4；所有模块都要确认当前 Android、目标应用或 Native 目标在作者支持范围内；
5. 只保留一个待测试模块并完整重启；
6. 启动目标后刷新 YukiZygisk 页面，分别看 Zygote 注入、普通模块库存与 Native 目标监视器，再用 daemon/core 日志判断普通模块是否实际加载；
7. 从管理器保存/分享完整 bugreport，而不是只复制实时日志最后几行。

Native 状态必须按字面区分：

- **未知**：可能尚未观察到目标，也可能已经检测/重定向但还没有明确成功或失败报告；先启动目标，再结合原始状态与日志判断；
- **已观察到目标进程，但模块注入未完成**：才是明确的模块/目标失败；
- **已注入**：证明运行时完成了注入路径，仍不自动证明模块最终功能正确。

同名 Zygote 的 PID 发生 3 次更替后，YukiZygisk 会进入注入安全模式并停下注入；这个计数能证明进程重启，不能单独证明崩溃原因。先关掉最近加的模块并完整重启，再按[功能与状态](/yukizygisk/features/)区分 Zygote 与 [Native ZN](/yukizygisk/native-zn/)证据。

## 更新后功能异常

按版本层拆分检查：

- 只更新了管理器 APK？
- 是否同步了设备侧 `ksud`？
- LKM 是否也改变？KMI 是否相同？
- MetaModule 是否处于待更新状态？
- 普通模块或 YukiZygisk 模块是否同时更新？

最有价值的结论是：“这套版本原本正常，只改了 X 就坏了。”一次把 APK、`ksud`、LKM 和模块全更新，再说“最新版坏了”，谁都只能靠猜。

## 设备无法启动

别继续乱刷，也别随机切槽位。先记下最后改了哪份镜像、哪个分区、哪个槽位，再按[救砖与恢复](/guide/rescue-bootloop/)回到确定能启动的状态。

如果问题发生在安装普通模块之后，优先尝试安全模式或禁用最近模块；如果发生在刷写 LKM 后且 Android 从未启动成功，应优先恢复原厂镜像，而不是从模块层排查。ImgPatch 修改的是 `boot` 内的内核 Image，即使同一设备的传统 Ramdisk 路径平时使用 `init_boot`，恢复时也必须按实际工作模式找对分区。

Lateload 本身在重启后不会继续加载 LKM。若一次临时会话之后发生持久启动问题，应另外核对这次会话是否安装了模块、改了分区或保存了其他启动配置，不能只把原因写成“开过越狱模式”。

## 提交问题前

一份可用的问题报告至少包含：

- 设备型号、Android 构建指纹、原始/当前内核版本与架构；
- YukiSU LKM、管理器、内置/已安装 `ksud` 完整版本；不匹配时保留已安装侧“未知”的原始状态；
- Hook 类型、工作模式、目标 KMI、实际分区与槽位；
- 输入镜像来源、修补/写入输出与可用备份；
- MetaModule、相关模块与 Feature 状态；
- YukiZygisk 模块类型、ABI、目标与运行时状态（如涉及）；
- 问题出现前最后一次改动；
- 可重复的最短步骤；
